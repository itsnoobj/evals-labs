The takeaway in one line

"Which metrics would have caught that?"

1. Break it

Take one real model run. Click "reply states ₹2,500, tool said ₹250". The 8 metric tiles re-score instantly.

2. See who missed it

Most tiles stay green. People see that answer-only and trajectory-only checks both miss it, and that only a grounding check catches it.

3. Rerun and trust the spread

Run the 12-case golden set 5 times. The average looks fine, the grid shows which cases flip. Same prompt, different results.

Checked against the WebLLM source

What the browser model can and cannot do

Supported

  • JSON mode and a seed field for reproducible output (WebLLM README).
  • Small prebuilt models, for example SmolLM2-360M (q4f16: 376 MB VRAM, needs shader-f16; q4f32: 580 MB VRAM) and Qwen2.5-0.5B (q4f16: 945 MB VRAM). Source: src/config.ts.
  • Serving as static files, so GitHub Pages works.

Constraints that shape the design

  • Native function calling is marked WIP. The plan uses JSON mode plus our own parser, which also gives clean "invalid JSON" and "invented tool" failures to measure.
  • It needs WebGPU. Phones and some browsers will not run it, so a replay mode serves recorded real runs.
  • VRAM figures are not download sizes. I do not know the download size yet. S1 measures it.

Devil's advocate

Top 3 risks

Risk 1

The tiny model is hopeless

Failure: a 360M model may score near 0% or produce invalid JSON on most steps, so every grid is red and nothing is learned.

Fix: S1 gate with numbers. Constrain each step with JSON mode and a short tool list. Fall back to Qwen2.5-0.5B or a simpler task.

Risk 2

Nobody can run it

Failure: no WebGPU on phones, slow venue Wi-Fi, and a model download on first click.

Fix: replay mode with real recorded runs, a pre-cached model on your laptop, and Screen 2 works without any model.

Risk 3

Metrics look like theater

Failure: a keyword "answer match" is not a real judge, so people discount the lesson.

Fix: label stand-ins plainly, show the tiny model-judge flipping, and add the calibration screen in v1.1.

Over-engineered? The Web Worker and replay mode add code, but both are required: the worker keeps the UI responsive during generation, replay covers visitors without WebGPU. No framework, no build, no config.
Simpler option: ship only Screen 2 (metrics board) with recorded runs. About 1 hour, no model risk. You lose the live-model and variance lessons.
